## 第一性原理边界

1. 地址只负责路由。loopback 不能证明请求者是谁；本地后端仍需要认证。
2. 私有代理通道证明“这些证书字段来自受信代理”，证书账号再匹配安装时指定的 `NAS_USER_ID`。这不是自动识别小米所有管理员角色，也不是任意家庭成员授权。
3. `0600` 的代理配置/密钥防止普通本机账号读出代理口令，不抵抗 root 或与服务同 UID 的进程。共享同一 Web origin 的插件仍处于同一前端信任域，禁止把它称为第三方不可信代码隔离。
4. 已认证不等于文件相同；长度、时间和旧记录都不能替代内容检查。
5. 回滚必须包括进程状态，不能只恢复文件。当前处理正常异常，不承诺断电、SIGKILL、磁盘损坏时自动恢复。

## 第二批：离线依赖门禁

新增 `shared/offline_dependencies.py`，市场和 115 独立安装端不再测速后联网 root pip。改为精确版本、全文件 SHA-256 锁、签名包内 wheelhouse；禁用源码构建、直接 URL 依赖与 pip 配置覆盖。临时目录完成安装后才发布 `lib/`，失败不留下半套运行依赖。Windows/Mac 启动器及市场发布包均携带此模块。

构建前预检会在签名密钥访问和输出写入前拦截缺包。当前 115 没有受审完整 wheelhouse/锁文件，按设计拒绝构建和安装，绝不声称“离线包已完成”。17 个固定版本均查询到官方 PyPI 元数据，oss2/crcmod 没有现成 wheel；后续需要隔离 ARM64 构建与真实 SDK 验收。详见 [离线依赖准备与边界](OFFLINE-DEPENDENCIES.md)。

本批重新运行公共/依赖测试 20 项、市场 24 项、115 10 项，共 54 项通过，无跳过。含 15 项新增依赖测试、3 项新增安装/发布集成测试；真实本机 pip 覆盖成功、缺间接依赖、平台不匹配，PowerShell 夹具随市场回归通过。两个改动 shell 安装器 `bash -n` 及 `git diff --check` 通过。这 54 项不是重新宣称第一批所有插件或实际 NAS 全量验收通过。

中继身份暂不改代码：离线提取的 Mac 客户端中可见证书 HTTPS Agent、`requestPluginToken`、`pluginTokenManager` 等路径，但客户端有 token 刷新逻辑不等于后端已经验证当前调用者。尚缺 NAS 验证端及局域网/P2P 两条路径的闭环证据，不能凭函数名接受 token、信任请求自报账号，或恢复本机免鉴权。当前生产设备保持原样。

## 尚未完成及发布门禁

- 不能直接部署：真实 Mac/安卓的中继路径未验收。没有可靠证书身份的中继会被拒绝，必须验证官方信任链或设计独立配对机制，不能恢复 loopback 放行来掩盖兼容问题。
- 尚未实现低权限 API 与固定操作特权代理拆分、每插件进程/数据隔离；root 和 Docker socket 的完整隔离属于下一阶段。
- 尚未完成持久化事务日志、断电恢复、独立云盘旧安装器的统一事务迁移，以及受审依赖产物的完整准备。第二批已落地 wheel/哈希执行门禁，但不能把门禁等同于依赖包已制成。旧云盘任务的存储根收缩需要显式迁移方案，未偷偷修改任务路径。
- 无远端内容哈希时，每次读取下载内容会增加带宽；真实账号应测量后再优化，不能再回退为只比较大小。普通用户改名/替换父目录的完整竞争防护还需 dirfd/目录身份机制。
- `shared/plugin_security.py`、服务配置、nginx 模板必须作为一个版本整体发布，不能只替换服务器脚本。代理配置含密钥，不能公开上传或附到故障截图中。
- 当前 `catalog`/`artifacts`/旧 ZIP 不包含本轮修复。必须完成源码验收后，在新的输出目录重新构建、签名、扫描、核对版本，再做 Windows 10/11 和 RP05 双端真实验收。未使用正式发布私钥。
